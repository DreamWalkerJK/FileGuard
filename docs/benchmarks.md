# 性能基准

2026-09-13 本机实测：Windows 10.0.26200、.NET 10.0.2、Release、NVMe SSD、18 个逻辑处理器。使用生成数据，文件刚写入，缓存处于热状态；不能将大文件结果当作冷盘吞吐量。

| 指标 | 大量小文件 | 少量大文件 |
| --- | ---: | ---: |
| 文件数 | 10,000 | 8 |
| 单文件大小 | 1,024 B | 67,108,864 B |
| 总字节数 | 10,240,000 | 536,870,912 |
| 并发度 / Channel 容量 | 2 / 64 | 2 / 64 |
| 扫描及分组耗时 | 260.848 s | 0.446 s |
| 峰值工作集 | 76,828,672 B（73.27 MiB） | 49,074,176 B（46.80 MiB） |
| CPU 时间 | 156.109 s | 0.703 s |
| CPU 使用率（相对一个核心） | 59.85% | 157.80% |
| 错误数 | 0 | 0 |
| 大小筛选候选数 | 10,000 | 8 |
| 完整 SHA-256 数 | 10,000 | 8 |
| 重复组数 | 100 | 4 |

计时包含目录遍历、大小筛选、完整 SHA-256、SQLite 索引写入及重复组查询；不包含测试数据生成。峰值内存是进程整个生命周期的工作集峰值，因此包含数据生成。CPU 百分比可超过 100%，因为多个工作者并行使用多个核心。本轮没有强制清除 OS 缓存、没有对系统其他进程做隔离，也不是专业存储吞吐测试。

小文件基准暴露当前逐文件 SQLite 持久化及安全句柄检查的开销；这是已知性能限制。当前优先保留明确持久化边界与有界流水线，不使用未经测量的 ArrayPool 优化。大量小文件场景应预留足够扫描时间。

复现命令（从仓库根目录执行）：

```powershell
dotnet run --project benchmarks/FileGuard.Benchmarks -c Release -- small 2
dotnet run --project benchmarks/FileGuard.Benchmarks -c Release -- large 2
```

原始无敏感路径 JSON 在忽略目录 `artifacts/benchmarks/small.json` 和 `large.json`。生成文件只在 `.test-data/benchmarks/`。`FILEGUARD_BENCH_STORAGE` 可为 JSON 填入存储介质说明；本轮通过 Windows `Get-PhysicalDisk` 和卷映射另行确认 NVMe SSD。

逻辑重复大小和预计物理回收不是相同概念。硬链接共享块，稀疏/压缩/快照可能继续持有数据；隔离本身不会释放同卷空间，永久清除后的实际物理回收值无法可靠测量时返回 null。
